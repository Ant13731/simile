
\subsection{Operational Semantics}
Let $\sigma$ represent the symbol table (data store) for assigned variables, defined types, and procedure definitions. Further, let $\bot$ represent an error state; any operations that do not explicitly handle the error state are expected to propagate the error. The following sections define small-step semantics for Simile in the form of inference statements from $\langle$Simile code, $\sigma \rangle \to \langle$Derived simile code, $\sigma' \rangle$. When $\sigma$ does not change between steps, it is excluded for brevity. Generally, notation in the hypothesis section of each statement will correspond to set theory; notation in the inference corresponds to Simile code.

\paragraph{Values of Types}
The following are models of value sets in Simile. Although we try to follow set theory where possible, some types opt for more conventional programming styles for ease of use and relevance to programming. Let value $v$ be defined as any of the following:
\begin{grammar}
<v> ::= <a> | <b> | <i> | <f> | <q> | <t> | <s> | <r> | <B> | <S> | <R>
\end{grammar}
\subparagraph{None}
\begin{grammar}
<a> ::= `none'
\end{grammar}
\subparagraph{Bool}
\begin{grammar}
<b> ::= `true' | `false'
\end{grammar}
\subparagraph{Int}
\begin{grammar}
<i> ::= [-][0-9]+
\end{grammar}
where $i \in -\infty \upto \infty$
\subparagraph{Float}
Let $i_N$ be an int constrained such that $-2^{N-1}+1 \leq i_N \leq 2^{N-1}$. Then,
\begin{grammar}
<f> ::= [-][0-9]*`.'[0-9]+
\end{grammar}
64-bit floats following IEEE-754 %TODO cite
with variables $e_{bits} = 11, m_{bits} = 52, e = 2^{e_{bits}}-1023, m = 2 \times 2^{m_{bits}}$
where $-2^e\times m \leq f \leq 2^e\times m$. Effectively, floats follow $ -1.79\times 10^{308} \leq f \leq 1.79\times 10^{308}$.
\subparagraph{String}
\begin{grammar}
<q> ::= `"' [\^{}`"']* `"'
\end{grammar}
with additional semantics like:
\begin{grammar}
<q'> ::= `\{\}' | `\{'<i> \lit{$\mapsto$} <q> \{`,' <i> \lit{$\mapsto$} <q> \}`\}'
\end{grammar}
where $min(dom(q')) = 0$ and $max(dom(q')) = |q'|$ (ie. it is a sequence of characters).
\subparagraph{Tuple}
\begin{grammar}
<t> ::= `()' | `(' <value> `,)' | `(' <value> `,' <value> \{`,' <value>\}`)'
\end{grammar}
\subparagraph{Set}
\begin{grammar}
<s> ::= `\{\}' | `\{' <value> \{`,' <value>\}`\}'
\end{grammar}
\subparagraph{Relation}
\begin{grammar}
<r> ::= `\{\}' | `\{' <value> \lit{$\mapsto$} <value> \{`,' <value> \lit{$\mapsto$} <value>\}`\}'
\end{grammar}
Further, $relation[T_1, T_2] = set[(T_1, T_2)]$ and carry all semantics associated with that type.
\subparagraph{Bag}
\begin{grammar}
<B> ::= `\{\}' | `\{' <value> \lit{$\mapsto$} <i> \{`,' <value> \lit{$\mapsto$} <i>\}`\}'
\end{grammar}
where $\forall i \in ran(B) | i \geq 0$. Further, $bag[T] = relation[T, int]$ and carry all semantics associated with that type.
\subparagraph{Sequence}
\begin{grammar}
<S> ::= `\{\}' | `\{' <i> \lit{$\mapsto$} <value> \{`,' <i> \lit{$\mapsto$} <value>\}`\}'
\end{grammar}
where $min(dom(S)) = 0$ and $max(dom(S)) = |S|$, Further, $sequence[T] = relation[int, T]$ and carry all semantics associated with that type.
\subparagraph{Record}
\begin{grammar}
<R> ::= <constructor> `()' | <constructor> `('<value> \{`,' <value>\}`)'
\end{grammar}
where the constructor identifier is the same as the type identifier. Records act like a named, ordered tuple; effectively a $relation[str, T]$ where $T$ may be any combination of types. Let record $R'$ be defined with fields $f_1, f_2, ...$. Then the view $R': relation[str, T] = \Set{f_1 \mapsto v_1, f_2 \mapsto v_2, ...}$ can be used. The type is inherently ordered, so there is a another relational view: $R_{type}: relation[int, type[T]] = \Set{0 \mapsto v_{type_1}, 1 \mapsto v_{type_2}, ...}$. image on the type

\subparagraph{Equals} For primitives, equality is calculated in the usual mathematical manner. We explicitly specify equality for collection types, although these also follow convention.
\begin{gather}
  \tag{Primitives}
  \begin{prooftree}
    \hypo{T \in \Set{none, bool, int, float, str, enum}}
    \hypo{v_1, v_2: T}
    \hypo{b: bool = (v_1 = v_2)}
    \infer3{\texttt{v_1 = v_2} \to \texttt{b}}
  \end{prooftree}
  \\
  \tag{Tuple}
  \begin{prooftree}
    \hypo{t_1: (T_1, T_2, ...)}
    \hypo{t_2: (T_1, T_2, ...)}

\subparagraph{And} To enable the optimizer to shuffle around $\land$-conditions within programs following discrete maths, we cannot use the programming-specific short-circuiting features. Conventional short-circuiting evaluates conditions from left to right, stopping at the first annihilating clause (false for $\land$, true for $\lor$). However, this can hide potentially $\bot$-valued clauses to the right of the annihilator. So, when the optimizer leans on commutativity to reorder clauses, behaviour would not be guaranteed. Optimistic short-circuiting keeps the same idea as short-circuiting, but extends it to recover from $\bot$-valued clauses when an annihilator is present in any clause. We only pay an efficiency penalty in the case where we would otherwise throw an error.
\begin{gather}
  \tag{And}
  \begin{prooftree}
    \hypo{b_1, b_2, b_3: bool}
    \hypo{b_3 = (b_1 \land b_2) = (b_2 \land b_1)}
    \infer2{\texttt{b_1 and b_2} \to \texttt{b_3}}
  \end{prooftree}
  \\
  \tag{Optimistic short-circuiting (left)}
  \begin{prooftree}
    \hypo{b: bool}
    \hypo{v \in \Set{\bot, b}}
    \infer2{\texttt{false and v} \to \texttt{false}}
  \end{prooftree}
  \\
  \tag{Optimistic short-circuiting (right)}
  \begin{prooftree}
    \hypo{b: bool}
    \hypo{v \in \Set{\bot, b}}
    \infer2{\texttt{v and false} \to \texttt{false}}
  \end{prooftree}
\end{gather}

\paragraph{Arithmetic} % TODO what about precision? Do we define a max precision? See how WASM does it
Integers follow unbounded precision arithmetic, while floats follow IEEE-754. Addition is commutative for pure-int operations (and thus can be used in the optimizer more freely), while floats remain bound by the written order because of precision limitations. Multiplication and exponentiation are semantically defined in terms of addition, and thus follow similar semantics: close to mathematics for ints, close to programming for floats.
